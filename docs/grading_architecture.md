# Grading Architecture Specification

**Project:** SurveyML-Eval
**Document:** Grading Architecture Specification
**Version:** 1.0
**Status:** Proposed architecture
**Checkpoint:** CP-06E

---

## 1. Purpose

This document defines the grading architecture for SurveyML-Eval.

The grading architecture specifies how responses generated by large language models (LLMs) will be evaluated against benchmark task requirements and reference criteria.

It establishes a consistent and auditable grading pipeline that supports deterministic evaluation, rubric-based assessment, expert review, and statistical analysis of model performance.

The architecture prioritizes grading reliability, fairness, transparency, and reproducibility.

## 2. Grading Design Principles

The grading architecture follows these principles:

1. **Consistency:** Equivalent responses must be evaluated using the same grading criteria.
2. **Deterministic evaluation:** Exact and objectively verifiable answers should use deterministic grading wherever appropriate.
3. **Rubric transparency:** Subjective and analytical responses must use documented scoring rubrics.
4. **Partial credit:** Responses demonstrating valid intermediate reasoning should receive appropriate credit.
5. **Expert oversight:** Statistical and methodological correctness must be reviewed by qualified experts where automated assessment is insufficient.
6. **Grading independence:** Grading logic must not depend on the model provider.
7. **Auditability:** Every score must be traceable to its response and grading configuration.
8. **Reproducibility:** Grading rules and versions must be preserved.
9. **Fairness:** Equivalent answers and justified alternative methods must be treated consistently.
10. **Research integrity:** Automated grading decisions must not be represented as expert-verified unless human review has occurred.

## 3. High-Level Grading Architecture

The proposed grading pipeline contains:

1. Grading configuration loader.
2. Response loader.
3. Response validation module.
4. Reference answer loader.
5. Deterministic grading engine.
6. Rubric-based grading engine.
7. Critical error detection module.
8. Human review interface.
9. Score aggregation module.
10. Grading audit and reporting module.

The grading pipeline consumes eligible model responses and produces structured grading records.

It must remain separate from model execution so that the same grading criteria can be applied across different providers.

## 4. Grading Methods

SurveyML-Eval will support multiple grading methods depending on the nature of each task.

### 4.1 Deterministic Grading

Deterministic grading is suitable for objectively verifiable outputs.

Examples include:

- Exact numerical answers.
- Numerical answers within predefined tolerances.
- Required JSON fields.
- Valid categorical selections.
- Mathematical calculations.
- Expected variable names.
- Required output elements.

The grader must document normalization and comparison rules.

Floating-point comparisons should use explicitly defined tolerances rather than unrestricted exact string matching.

### 4.2 Rubric-Based Grading

Rubric-based grading is appropriate for analytical and explanatory responses.

It may evaluate:

- Statistical reasoning.
- Method selection.
- Interpretation.
- Methodological justification.
- Identification of assumptions.
- Uncertainty assessment.
- External validation reasoning.
- Limitations and caveats.

Each criterion must have a defined scoring range and evidence requirements.

### 4.3 Hybrid Grading

Hybrid grading combines deterministic checks and rubric-based assessment.

For example, a task may require:

- A numerical performance metric.
- Correct interpretation of the metric.
- Justification of the selected evaluation method.

The numerical component may be graded deterministically, while the interpretation and justification are assessed using a rubric.

## 5. Grading Rubric Structure

Every rubric-based task must define:

- Criterion identifier.
- Criterion description.
- Maximum points.
- Scoring levels.
- Expected evidence.
- Critical error conditions, where applicable.
- Accepted alternative reasoning.

A rubric must be defined and reviewed before evaluating model responses.

Scoring criteria must correspond to the task objective and benchmark grading framework.

## 6. Partial Credit

The grading system must support partial credit.

Partial credit is appropriate when a response demonstrates some valid knowledge but does not fully satisfy the task.

Examples include:

- Correct method with incomplete justification.
- Correct calculation with incomplete interpretation.
- Correct identification of survey weights but incorrect variance interpretation.
- Correct validation strategy with incomplete explanation.
- Recognition of distribution shift without adequate assessment.

Partial credit must be based on documented scoring rules rather than subjective preference.

A missing critical requirement may prevent full credit even when other parts of the response are correct.

## 7. Critical Error Detection

Some errors may indicate serious methodological misunderstandings.

The grader should identify task-specific critical errors such as:

- Treating survey weights as ordinary predictive features without justification.
- Ignoring complex survey design when it is necessary for the requested inference.
- Using test data for model selection.
- Allowing target leakage.
- Reporting external validation as internal validation.
- Making unsupported causal claims from predictive associations.
- Misinterpreting uncertainty estimates.
- Reporting performance metrics without their required context.

Critical errors must be explicitly defined in the relevant task rubric.

A critical error should not automatically imply a zero score unless the task-specific rubric defines that consequence.

The grading record should preserve both the numerical score and critical error indicators.

## 8. Reference Answer Management

Reference answers must remain separate from model-facing task definitions.

The grading system should retrieve reference information using the task_instance_id.

Reference materials may contain:

- Expected numerical answers.
- Accepted alternative answers.
- Reference calculations.
- Statistical interpretations.
- Methodological requirements.
- Grading rubrics.
- Critical error definitions.
- Expert review notes.

Reference answers must not be included in prompts sent to evaluated models.

Changes to reference answers or grading rubrics must be versioned.

## 9. Deterministic Grading Workflow

The deterministic grading workflow follows these steps:

1. Load the model response.
2. Validate response completeness.
3. Parse the required response format.
4. Normalize permitted formatting differences.
5. Extract relevant answer components.
6. Compare outputs against reference criteria.
7. Apply numerical tolerances where appropriate.
8. Calculate criterion-level scores.
9. Record validation errors.
10. Store the grading result.

Normalization must not change the substantive meaning of a response.

Invalid or incomplete outputs must be recorded rather than silently corrected.

## 10. Rubric-Based Grading Workflow

The rubric-based workflow follows these steps:

1. Load the response and task-specific rubric.
2. Identify the required response components.
3. Evaluate each scoring criterion.
4. Record supporting evidence from the response.
5. Apply partial credit where justified.
6. Identify critical errors.
7. Calculate the total score.
8. Record reviewer or grader identity.
9. Preserve criterion-level decisions.
10. Store the final grading record.

Where subjective assessment is required, the rubric must provide sufficient guidance to reduce evaluator disagreement.

## 11. Human Expert Review

Human expert review is necessary when automated evaluation cannot reliably determine correctness.

Expert review may be used for:

- Complex statistical reasoning.
- Alternative methodological approaches.
- Interpretation of survey design.
- Justification of validation strategy.
- Assessment of nuanced uncertainty statements.
- Ambiguous or incomplete responses.
- Disputed grading outcomes.

Reviewers should receive the task definition, model response, and applicable rubric.

Hidden reference information may be provided to authorized reviewers.

Human review decisions must be documented with criterion-level scores and supporting explanations.

## 12. Inter-Rater Agreement

When multiple reviewers assess the same response, inter-rater agreement should be evaluated.

The appropriate statistic depends on the scoring design.

Possible measures include:

- Cohen's kappa for suitable two-rater categorical assessments.
- Weighted kappa for suitable ordinal assessments.
- Fleiss' kappa for suitable multi-rater categorical assessments.
- Intraclass correlation coefficients for appropriate numerical ratings.

The selected statistic, its assumptions, and its interpretation must be documented.

Agreement estimates should be reported with appropriate uncertainty where feasible.

High agreement does not automatically establish grading validity.

## 13. LLM-Assisted Grading

LLM-assisted grading may be explored as a supplementary evaluation method.

However:

- It must not serve as the sole ground truth.
- Its model identifier and version must be recorded.
- Its grading prompt must be versioned.
- Its scoring rubric must be preserved.
- Its outputs must be auditable.
- Its agreement with deterministic or expert-reviewed assessments must be evaluated.

Potential biases, inconsistencies, and sensitivity to response wording must be investigated.

LLM-assisted scores should be distinguished from human-reviewed and deterministic scores in reporting.

## 14. Score Calculation and Aggregation

Each task instance must define a maximum score.

Criterion-level scores must be aggregated using documented rules.

For a task with criteria \(1,\ldots,m\), a simple additive score can be expressed as:

\[
S_i = \sum_{j=1}^{m} s_{ij}
\]

where:

- \(S_i\) is the total score for response \(i\).
- \(s_{ij}\) is the score obtained on criterion \(j\).

If criterion weights are used, the aggregation formula must be specified in advance.

Scores must be checked against their permitted minimum and maximum values.

Task scores should be normalized only using documented and consistent rules.

## 15. Grading Record Structure

Every grading result must contain sufficient information for audit and reproducibility.

Required fields should include:

- grading_id
- grading_version
- execution_id
- response_id
- task_instance_id
- model_id
- trial_id
- grading_method
- rubric_version
- criterion_scores
- total_score
- maximum_score
- critical_errors
- reviewer_id, where applicable
- grading_status
- graded_at

The record must distinguish automated grading from human review.

## 17. Grading Storage Structure

The proposed grading storage structure is:

```text
results/
├── raw_outputs/
├── graded_outputs/
│   ├── deterministic/
│   ├── rubric_based/
│   ├── human_review/
│   └── llm_assisted/
├── scores/
│   ├── criterion_scores/
│   ├── task_scores/
│   └── model_scores/
└── reports/
```

Raw model outputs must remain separate from grading records.

Grading records should reference original responses rather than replacing or modifying them.

## 18. Grading Validation and Quality Assurance

The grading system must be tested before benchmark results are reported.

Validation should include:

- Correct reference answer tests.
- Incorrect answer tests.
- Boundary-value tests.
- Numerical tolerance tests.
- Partial-credit tests.
- Critical error tests.
- Malformed response tests.
- Missing response tests.
- Rubric consistency tests.
- Reviewer agreement assessment.

Grading changes must be versioned.

Previously generated scores must remain traceable to the grader and rubric versions used at the time.

## 19. Relationship with Other Components

The grading architecture integrates with:

- Repository architecture.
- Benchmark task schema.
- Dataset schema.
- Execution architecture.
- Reference answer storage.
- Statistical evaluation pipeline.
- Result aggregation.
- Reporting system.

The execution engine supplies model responses.

The task and reference definitions supply evaluation requirements.

The grading engine evaluates responses and generates auditable score records.

The statistical analysis pipeline uses these records for benchmark-level comparisons.

## 20. Implementation Boundaries

This checkpoint defines the logical grading architecture.

It does not implement:

- Complete deterministic graders.
- Automated rubric evaluation.
- Human review interfaces.
- LLM-as-a-judge services.
- Inter-rater agreement calculations.
- Complete score aggregation scripts.
- Actual experimental model scores.

These components will be implemented and validated incrementally.
